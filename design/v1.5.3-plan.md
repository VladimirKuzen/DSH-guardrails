## Q-1 多目标删除被当成单目标静默

**证据**（live policy，`roots` 含 `Guardrails`、`paths` 含 `_scratch`；两个探针文件先建好）：

```text
Remove-Item -LiteralPath "...\Guardrails\_scratch\q1.tmp" -Force                         -> exit 0（静默，正确）
Remove-Item -LiteralPath "...\Guardrails\_scratch\q1.tmp","...\Guardrails\_scratch\q2.tmp" -Force -> exit 0（应 2）
```

第二条把两个文件一起删了，却走了静默放行。

**补充证据（2026-11-24，live 1.5.2）**：清理 `_scratch` 时用
`Remove-Item -LiteralPath _dbg.ps1,_t.ps1,_t2.ps1 -Force` 一次删三个文件，同样**未弹卡、直接执行**——
说明该缺陷不只出现在 `-LiteralPath` 带引号全路径的写法里，裸相对文件名列表也一样。

**判定在哪一行**：

- `lib/facts.js:173-174`：`PATH_FLAG` 只取**第一个**参数，`facts.target` 因此只有一个；
- `lib/facts.js:356-358`：`count` 由该目标的 `stat` 得出，文件存在即 `1`；
- `lib/rules/quiet.js:82`：只校验 `facts.count !== 1`——`count` 已经是 1，条件通过；
- `test/quiet.test.mjs:136` 的 "more than one target asks" 注入的是 `facts({ count: 2 })`，
  没有覆盖"命令文本里真写了两个路径"。

**改法**：在该语句内数路径实参（引号内的盘符/UNC + `-Path` 旗标后的裸 token），多于一个就否决；
或在 `facts` 里给出 `targetCount`，由 `quiet.js` 判断。**新增契约用例两条**：引号列表、
`-Path "a","b"`，断言 `quiet:false`。

**证伪**：上面第二条命令的 `check.mjs` 退出码从 `0` 变 `2`。

## Q-2 `paths` 相对会话工作区匹配

**证据**：

1. `paths` 现在是相对 `roots` 的**首段**匹配（`lib/rules/quiet.js:100-104`）。把 `roots` 换成父目录
   `D:\My Documents\deepseek-harness` 后，`...\Guardrails\_scratch\x.tmp` 的首段变成 `Guardrails`，
   不再命中 `_scratch`——**静默范围反而归零**。
2. 若为让它生效而把工作区名写进 `paths`，静默范围从"临时目录"扩成"整个工作区的任意单文件删除"
   （含 `dsh-guardrails\lib\*.js`）；叠加 Q-1，连双文件删除都会静默。
3. `paths` 只收单段（`lib/rules/quiet.js:48-58`），写 `Guardrails\_scratch` 会被判 `config-invalid`，
   静默整体关闭。
4. 现状下 `D:\My Documents\deepseek-harness` 的 10 个工作区里只有 `Guardrails` 有 `_scratch`
   （2026-11-21 20:07 实测），`build` / `dist` 一个都没有。
5. 审计 `audit-2026-11-15.jsonl` 里的真实拦截都不在白名单能覆盖的形状里：`Hardware Price` 根目录的
   相对路径双目标删除（06:26）、`dsh-guardrails\README.md` 相对路径（11:35）、`-Recurse`（11:38、14:50）、
   目标不存在导致 `count` 不可得（14:15）。工作区**根目录**的单文件删除在任何配置下都不会静默
   （`lib/rules/quiet.js:104` 的 `relative === first`）。

**改法**：`roots` 继续表示受信工作区父目录；`paths` 改为相对**会话 cwd**（工作区根）匹配，并要求
target 在该工作区之下；`alwaysAsk` 语义不变。cwd 未知时**不静默**（当前是"未知也放行"，
`test/quiet.test.mjs:108` 的 "an unknown cwd does not disable quiet" 要翻牌）。

**待定（实现前必须拍板）**：

- `roots` 是否仍要同时约束 cwd 与 target（防止"在 A 工作区删 B 工作区"）；
- `rules.destructive.workspaceQuiet` 旧键的迁移要不要在这版一起收口；
- cwd 未知时翻成"不静默"属于**加严**，要不要在同一版给 `--deep` 之类的诊断出口（不是必须）。

**证伪**：在 `Hardware Price` 会话里删 `...\Hardware Price\_scratch\x.txt` 静默，而同一工作区内、
`_scratch` 之外的单文件删除仍弹卡。

## Q-3 与外来 hook 插件的实地共存验证

**背景**：2026-11-24 新机（LAPTOP-AG91ACN9）1.5.1 → 1.5.2 升级演练全部通过，其中"冲突检测"验的是
**同一个插件被装两份**（`guardrails-old@npm:…@1.5.1` 别名 → doctor 报两条依赖 + bundles 出现两次 →
移除后恢复）。还没有证据的是**另一个插件也挂 `tools/pre-execute`** 时的行为。`design/v1.5.2-self-check.md`
§9 已把"`--deep` 的措辞未在真装 cc-safety-net 的机器核对"标为未验证，本条就是补这一格。

**要验的三件事**：

1. `doctor --deep` 在有外来 hook 的机器上会不会误报/漏报：预期列出 `suspected: <bundle>`，**退出码仍为 0**；
2. 两个拦截插件同时在场时，一次需要审批的删除是否仍只弹该弹的卡、能正常执行、不崩；
3. 卸载外来插件后，`doctor` 与 `doctor --deep` 是否回到全绿，`policy.json` 与 `audit/` 是否未被它改动。

**步骤（都记进报告，时间盒 10 分钟，顺序不要换）**：

```powershell
# 1) 基线：doctor --deep 应无 suspected
# 2) 装一个会拦 shell 的插件（cc-safety-net 是最贴近的例子）
& $dsh plugin --profile desktop add cc-safety-net
# 3) 不重启，直接 doctor --deep（文件扫描不需要重启），记录 suspected 行与退出码
# 4) 重启 DSH，触发一次需要审批的删除，记录卡片数量与执行结果
# 5) 卸载、重启、重跑 doctor 与 doctor --deep，必须全绿
& $dsh plugin --profile desktop remove cc-safety-net
```

**判据**：步骤 3 有 `suspected:` 或明确"没有别的 bundle 提到 hook"二者都算通过（`--deep` 只负责
列出疑似，从不用它判失败）；步骤 4 不得出现崩溃或重复执行；步骤 5 前后 `policy.json` sha256 一致。

**边界**：不用外来插件的表现评判本插件是否正确；它安装时弹卡、写自己的策略属预期噪音；若它的安装
触发本插件审批，按预演理由放行一次即可。**不做也不影响 1.5.3 的完成定义**——它是证据项，不是门槛。

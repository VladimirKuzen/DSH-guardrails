# v1.5.2 提案：自检与共存（2026-11-19）

> 性质：**提案**，不是已实现的设计。1.5.1 已发布、已收录，本文只讨论下一个补丁版本要不要做、做什么、不做什么。
> 2026-11-21 拍板：doctor 独立成文件、第 2 项检查藏在 `--deep` 后、npm 页面 README 手动同步（§7），
> 并新增第四个目标"插件能否正常更新"（§10）。

## 1. 起因

两件事同时发生：

1. 宿主发布了 `dsh-v0.2.2-rc.4` 与 `dsh-v0.2.2-rc.5`；本机已升到 rc.5 并按 `docs/DSH-API.md` 跑过五步验证（281bbdf 记录）；
2. 插件进入 dshmarket 收录流程后，用户会更容易在同一台机器上装到**第二个护栏类插件**（比如 cc-safety-net），
   而当两个插件都监听 `tools/pre-execute` 时，行为是两者叠加：可能两张卡、可能一个决定盖住另一个，
   顺序由宿主决定，我们无法控制。

`design/compare-cc-safety-net.md` §4 记过这件事，但那是"对比"，不是"我们能不能自己发现"。

## 2. 目标与非目标

**目标**

- 用户能在不读源码的前提下回答："现在到底有几个东西在拦我的工具调用？"
- 我们自己的安装异常（装了两份、版本与 `loaded.json` 不一致、策略被拒载）能被一条命令查出来。
- （新增）证明插件能从已发布版本**原地更新**到新版本，且更新后闸门仍在工作（§10）。

**非目标（明确不做）**

- 不改判定路径、不改规则表、不改审计格式——`git diff --stat` 对 `lib/`、`rules.js`、`index.js` 应为空。
- 不引入运行时依赖，不联网。
- **不自动停用自己**（理由见 §5）。
- 不承诺发现所有冲突：宿主没有暴露"谁注册了哪个监听器"的接口，我们只能从磁盘取证。

## 3. 版本兼容性（rc.4 / rc.5）

| 项 | 事实 | 对我们的影响 |
|---|---|---|
| rc.4 变更 | 模型请求异常响应的处理、LiveShare 桌面端创建分享失败 | 无插件 API 条目 |
| rc.5 变更 | DeepSeek 模型改用服务端搜索、其他模型默认 DeepSeek Search API | 无插件 API 条目 |
| 真正动插件作者的是 | rc.2：`tools.resolve` / `executable`、按步骤激活工具、原生与 PTC 执行拆成 Agent 作用域插件 | 那些改动针对**注册工具**；我们只监听、不注册，且已在 rc.3 上验收通过 |
| `engines.dsh` | 我们的范围 `>=0.2.0-0`，对 `0.2.2-rc.3` 用 dshmarket 同款 `satisfiesRange(…,{includePrerelease:true})` 实测 `true` | rc.5 同形，不会因版本号被拒装 |

我们依赖的六个面——`tools/pre-execute`、`tools/post-execute`、`session/event`、`{kind:'deny'|'ask'}`、
`exec.callId`、`exec.agent.session.header.cwd`——在 rc.4/rc.5 的发布说明里都没有出现。

但"说明没提"不等于"实际没变"。所以升级 rc.5 后**必须**跑 `dsh-guardrails/docs/DSH-API.md` 的五步验证，
其中只有 `loaded.json` 的 `version` + `surface: "ok"` 能证明"钩子还活着"（挂载成功 ≠ 会判定）。
在跑完之前，文档里不写"测于 rc.5"。

## 4. 方案对比

| 方案 | 做法 | 成本 | 风险 | 结论 |
|---|---|---|---|---|
| A. `doctor` 子命令 | 新增 `tools/doctor.mjs`，只读，按需运行 | 中（约 200 行 + 测试） | 低：不进判定路径 | **推荐** |
| B. 挂载时自检并告警 | 插件加载时扫一遍，写 `notice` 审计 + `logger.warn` | 低 | 中：每次启动都有开销与噪声；告警容易被忽略 | 可作为 A 的后续 |
| C. 自动停用自己 | 发现冲突就把 `enabled` 设 false 或不再返回决定 | 低 | 高：等于把闸门变成放行 | **不做**，见 §5 |

选 A 的理由：它是工具，不是闸门的一部分，因此不触碰 1.x 的语义约定；不进热路径，零平时开销；
测试可以用假的 profile 目录喂进来，不需要真的装第二个插件。

## 5. 为什么不自动停用

1. **做不到干净**。插件能做的"停用"只有两种：把策略改成 `enabled:false`（自我修改受保护状态），
   或不再返回决定（把闸门变成放行）。后者是静默降级，比两张卡危险。
2. **冲突不必然是"我们多余"**。若对方是 deny-only 且排在审批之后、我们是 ask，叠加的实际行为可能是
   "先问，被拒也拒"，未必需要谁退出。自动关闭等于替用户做安全决策。
3. **它会变成绕过面**。一个能因为环境里出现某个字符串就自我停运的闸门，可被伪造利用——
   这与我们整份设计（失败往安全侧倒、`criticalFallback`）相反。

替代：doctor 报出问题，README 加一节"和别的护栏插件一起用"，把选择权交给用户。

## 6. doctor 查什么

| # | 检查 | 判据 | 误报风险 |
|---|---|---|---|
| 1 | 我们是否装了两份 | profile 的 `dependencies` 里有两个条目解析到同一份源码（`@vlad/*` 与 `@vladimirkuzen/*`、`link:` 与 npm 并存） | 低 |
| 2 | 别的插件是否也监听 | 解析每个 bundle 的目录，扫源码里的 `tools/pre-execute` / `tools/post-execute`（排除其自身 `node_modules`，限额、2 秒预算） | 中：字符串命中不等于真挂，措辞必须是"疑似" |
| 3 | `loaded.json` 与包版本是否一致、`surface` 是否 `ok` | 直接比字段 | 低 |
| 4 | `policy.json` 能否通过校验 | 复用 `--validate` 的同一段代码 | 低 |
| 5 | 审计链是否完整 | 复用 `audit-report.mjs --verify` | 低 |

建议的接口（草案，未实现）：

```
node dsh-guardrails\tools\doctor.mjs                 # 人读
node dsh-guardrails\tools\doctor.mjs --json          # 给脚本
node dsh-guardrails\tools\doctor.mjs --profile web   # 指定 profile，默认 desktop
```

退出码沿用现有约定：`0` 全好；`1` 有问题；`2` 用法错误。第 2 项命中时**不改变退出码**，只作为警告列出
（因为它只是"疑似"）。

## 7. 决定（2026-11-21）

1. doctor 独立成 `tools/doctor.mjs`（方案 A）。理由：`tools/check.mjs` 是"单次调用进、单次裁定出"的求值器，
   退出码 0/2/3/1 的语义已经占满；doctor 是"扫安装状态、五项检查、人读+JSON"，参数集不同。
   独立文件让既有 CLI 契约测试一行都不用改。
2. 第 2 项（别的插件也 hook）做，但第一版藏在 `--deep` 后面（方案 C）：默认不打印，命中只作警告、
   不改退出码，措辞固定为"疑似"。等在一台真装了 cc-safety-net 的机器上核对过措辞再转正（1.5.3）。
3. npm 页面 README 手动同步：发版前把根 `README.md` 的当前内容同步进包内 `dsh-guardrails/README.md`，
   不引入发布脚本、不加新依赖；`package.json` 版本、CHANGELOG、tag 在 doctor 与 §10 的升级验证都通过后一起动。
   发版时机：上述两项验收全绿之后，不再单独为 1.5.2 攒批次。
4. 新增验证目标：**插件能否正常更新**（1.5.1 → 1.5.2），见 §10。它是发版门槛的一部分，不是可选项。

## 8. 验收（实现后）

- 全套 18 个测试文件仍全绿；新增 doctor 的测试用**临时目录**造 profile，不读写真实 `~/.dsh`；
- `git diff --stat` 对 `lib/`、`rules.js`、`index.js` 为空；
- 在本机跑一次 doctor，输出与 `~/.dsh/profiles/desktop/package.json` 的实际内容一致；
- 负向验证：手工造一个"两份同名包"的假 profile，doctor 必须报出来；
- 在临时 `DSH_HOME` 里完成 1.5.1 → 1.5.2 升级演练，doctor 五项全绿（§10-B）；
- `pnpm pack` 产物含全部运行必需文件，版本号与 tag 一致（§10-A）。

## 9. 未验证

- doctor 只能看到**已安装**的插件；运行中的临时挂载、Web profile 之外的宿主形态看不到。
- 字符串扫描对压缩/混淆过的 bundle 可能漏；对我们自己这种源码分发的包有效。
- 本机已升到 rc.5，2026-11-19 按 `docs/DSH-API.md` 五步验证通过（281bbdf）；rc.4 未单独测，rc.6+ 未测。
- `--deep` 的措辞尚未在"真装第二个护栏插件"的机器上核对过，1.5.3 再决定是否默认显示。

## 10. 验证目标：插件能否正常更新（2026-11-21 新增）

**问题**：1.5.1 已发布并被 dshmarket 收录。别人从 1.5.0/1.5.1 更新到 1.5.2 会不会坏？
我们至今只验证过"干净安装"和本机 `link:` 开发态挂载，**没有验证过替换已安装版本**。
更新是最容易静默出错的路径：旧文件残留、两份并存、`loaded.json` 停在旧版本、策略被覆盖、审计链被重置，
任何一项都不会让安装报错，只会让闸门悄悄失效。

**"正常"的五条判据**（全部满足才算通过）：

1. profile 里只有一份，`package.json` 的 version 是 1.5.2；
2. 运行文件没有旧版残留（`index.js`、`lib/`、`rules.js` 与新版一致，node_modules 里没有第二份 1.5.1）；
3. 重启后 `loaded.json` 的 `version` 为 1.5.2、`surface` 为 `"ok"`；
4. 既有 `policy.json` 原样保留、能通过校验（更新不得覆盖用户策略）；
5. 审计链继续追加，`audit-report.mjs --verify` 通过（更新不得清空或重置链）。

**A. 发版前，确定性检查（不联网）**

`pnpm pack` 后检查 tarball 文件清单：运行必需文件齐全——`index.js`、`rules.js`、`lib/`、`policy.schema.json`、
`cordis.patch.yml`、`locale/`、`i18n/`、`tools/`（含 `doctor.mjs`）、`icon.svg`；版本号与 tag 一致。
风险背景：`package.json` 的 `files` 字段漏一项，就是"更新成功但插件加载失败"——装的时候不报错，跑的时候没有闸门。

**A 的预演（2026-11-21，版本仍是 1.5.1）**：`pnpm pack` 得 41 个文件、79,244 字节，
`index.js`、`rules.js`、`lib/`（11 个）、`policy.schema.json`、`cordis.patch.yml`、`locale/`、`i18n/`、
`tools/`（`check.mjs`、`doctor.mjs`、`audit-report.mjs`）、`icon.svg`、`docs/`、`examples/`、`LICENSE`、
`README.md` 全部在，`test/`、`design/`、`node_modules/` 一个都没有。把 tarball 解到 `_scratch\pack\pkg-1.5.1`
后直接跑其中的工具：`tools/doctor.mjs --help` 退出 `0`、`tools/check.mjs` 对 `{"command":"git reset --hard"}`
退出 `2`，说明产物自带全部运行依赖。包内 `README.md` 是 27 行的指路页（不是仓库根 README 的副本），
1.5.2 的变更没有让它产生过期陈述，发版时只需再核一眼版本号与 tag 一致。

**B. 发版后，真升级演练（需网络；用临时 DSH_HOME 隔离）**

本机 profile 是 `link:` 开发态，直接 `dsh plugin add` 会覆盖 link 指向，所以演练必须在临时 home 里做：

```powershell
$env:DSH_HOME = "D:\My Documents\deepseek-harness\Guardrails\_scratch\upd-home"
dsh plugin --profile upd add @vladimirkuzen/dsh-guardrails@1.5.1
dsh plugin --profile upd add @vladimirkuzen/dsh-guardrails@1.5.2
node dsh-guardrails\tools\doctor.mjs --profile upd        # 期望五项全绿
```

再启动一次该 profile 使 `loaded.json` 落盘，`node dsh-guardrails\tools\doctor.mjs --profile upd` 复核。
`dsh plugin` 只转发 pnpm，不启动宿主；`loaded.json` 那一条需要宿主实际挂载才成立，所以"启动一次"是步骤而不是建议。

**C. 回滚与未验证的写法**

回滚 = `dsh plugin --profile upd add @vladimirkuzen/dsh-guardrails@1.5.1`。
若 1.5.1 拉不下来（网络/registry），在发布记录里写"升级路径未验证"，**不得写成通过**。
本机 `link:` 开发态不参与此演练；它由"重启后 loaded.json 版本+surface"这一条单独覆盖。

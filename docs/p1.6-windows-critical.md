# P1.6 — Windows 系统级操作硬停

> 状态：S1 已实现（提交 `116763a`），绕过面已收敛（提交 `87492a8`：launcher 剥壳、绝对路径、`regedit /s`、`failClosed`），S3 live 验收已通过（2026-11-15，插件 1.2.0）。
> 实现代码：`dsh-guardrails/lib/critical.js`、`rules.js`、`lib/facts.js`、`lib/describe.js`、`i18n/`。

## 1. 决策

| 项 | 决定 |
|---|---|
| 默认动作 | **deny**（不弹卡片，直接拒绝并把原因回给模型） |
| 覆盖范围 | 磁盘级、启动级、系统目录内容、系统目录权限、`HKLM\SYSTEM` / `HKLM\SAM` 配置单元 |
| 放宽方式 | policy 显式字段 `rules.critical.mode`，默认 `deny`；可改 `ask` / `off` |
| `diskpart /s` | 一律 critical（脚本内容不可见，无法确认目标盘） |
| `takeown` / `icacls` | 只有目标落在系统目录下才硬停；普通排障路径仍走 R2 ask |

## 2. 为什么是硬停而不是审批

这类操作同时满足三个条件：

1. **不可撤销**：改错就要外部介质才能恢复；
2. **无法当场验证**：必须重启才知道成败；
3. **依赖现场信息**：磁盘编号、分区表类型、是否双系统——模型从文本里无法确认。

审批卡只有一个“允许一次”按钮，挡不住误点；而 deny 能强制人回到自己的终端、对着磁盘管理界面操作。

## 3. 判定边界

### 硬停（critical → deny）

| 类别 | 命令 |
|---|---|
| 整盘格式化 | `format`、`format.com`、`format.exe`、`Format-Volume`、`Clear-Disk`、`Initialize-Disk`、`Remove-Partition` |
| diskpart 破坏性动词 | `clean`、`clean all`、`format`、`create/delete partition`、`create/delete volume`、`create/delete vdisk`、`convert` |
| diskpart 脚本模式 | `diskpart /s <file>`（内容不可见，一律硬停） |
| 引导配置 | `bcdedit` 的修改类动词（`/set`、`/delete`、`/create`、`/import`、`/export`） |
| 引导修复 | `bootrec /fixmbr`、`/fixboot`、`/rebuildbcd` |
| 卷影副本 | `vssadmin delete shadows`、`wbadmin delete` |
| 恢复环境 | `reagentc` 的修改类动词（`/disable`、`/enable`、`/setreimage`、`/setosimage`） |
| 系统配置单元 | `reg delete "HKLM\SYSTEM…"`、`reg delete "HKLM\SAM…"`、`Remove-Item HKLM:\SYSTEM` 等 |
| 系统目录内容 | 写/删/移 `%SystemRoot%`、`%ProgramFiles%`、`%ProgramFiles(x86)%` 下的路径（`copy` 只在目标是系统目录时算） |
| 系统目录权限 | `takeown` / `icacls` 且目标在系统目录下 |

`.exe` 写法（`reg.exe`、`diskpart.exe`、`bcdedit.exe`、`takeown.exe` 等）与裸命令等价。

### 放行（只读诊断）

| 命令 | 说明 |
|---|---|
| `Get-Disk`、`Get-Partition`、`Get-Volume` | 查询 |
| `diskpart` + `list disk` / `list volume` | 只读 |
| `bcdedit /enum` | 查看启动项 |
| `bootrec /scanos` | 扫描，不写 |
| `vssadmin list shadows` | 查看快照 |
| `reagentc /info` | 查看恢复环境状态 |

只读白名单要求**整条命令**都是只读（`bcdedit /enum & del …` 不算），并且先于 critical 破坏性匹配执行。

### 绕过写法（同一条命令的其它拼法）

| 写法 | 处理 |
|---|---|
| `cmd /c …`、`cmd /k …` | 剥掉 launcher 后对载荷重新判定，引号内的命令也会被扫描 |
| `powershell -Command …`、`pwsh -Command …` | 同上 |
| `Start-Process format …`、`Start-Process -FilePath diskpart …` | 剥掉 `Start-Process` 与 `-FilePath` 后判定 |
| 绝对路径 exe | `C:\Windows\System32\format.com D: /q /y`、`& "…\format.com" D:` 与裸命令等价 |
| `regedit /s evil.reg` | 脚本内容不可见，按 critical `registry` 处理 |

递归最多 2 层（`cmd /c "cmd /c …"` 到第二层即停）。反向要求：`Write-Host "format D:"` 只是输出文本，不算命令——只有 launcher 之后的引号片段才会被当作命令扫描。

### 仍走 R2 审批（危险但可撤销/范围有限）

- 注册表普通写入：`reg add`、`reg import`、`Set-ItemProperty HKLM:\Software\…`；
- 服务与计划任务：`sc create/config/failure`、`New-Service`、`schtasks /create|change|run`；
- 防火墙与防护：`netsh advfirewall set/reset`、`Set-MpPreference`；
- 磁盘修复工具：`chkdsk /f`、`dism /remove-*`、`dism /add-*`、`dism /cleanup-image`（`/scanhealth` 只读放行）、`sfc /scannow`。

## 4. 判定顺序

```
R3（密钥）
  └─ R1（DSH 自身目录）
       └─ R2c（critical：只读放行 → 破坏性硬停）
            └─ R2（普通破坏性，ask）
```

只读放行表必须**先于** critical 匹配，否则 `diskpart list disk` 会被 `diskpart` 一刀切误伤。

## 5. 数据模型

verdict 增加 `severity`、`category`、可选 `target`：

```json
{ "rule": "R2", "severity": "critical", "category": "systemfiles",
  "mode": "deny", "reason": "...", "target": "C:\\Windows\\win.ini" }
```

- `rule` 保持 `R2`（它本质仍是破坏性操作），`severity` 区分等级；
- `category` ∈ `disk` / `boot` / `systemfiles` / `permissions` / `registry` / `custom`；
- 审计记录增加 `severity`；
- `describe()` 用 `severity === 'critical'` 选择 ⛔ 前缀与 `action.<category>` 文案，`facts.target` 直接取 `verdict.target`。

## 6. 拒绝文案

面向模型、英文、可执行指令：

```
Guardrails R2 (critical): delete/overwrite inside a system directory (C:\Windows\win.ini) was refused.
This can make Windows unbootable or erase data, and the target cannot be verified from text.
```

`mode: "ask"` 时同一事实换成“requires explicit approval”的句子，卡片标题带 ⛔。

面向人的说明放在 README（S2），因为 deny 没有卡片可承载。

## 7. policy 形态

```json
{
  "rules": {
    "critical": { "mode": "deny", "patterns": [], "failClosed": true }
  }
}
```

- `mode: "deny"`（默认）：硬停；
- `mode: "ask"`：降级为审批卡（⛔ 前缀）；
- `mode: "off"`：完全交给普通 R2；
- `patterns`：追加自定义 critical 正则（命中记为 `custom`）；
- `failClosed: true`（默认）：判定流程自身抛异常时，仍然命中 critical 的 shell 调用会被拒绝——这是全插件唯一一处 fail-closed；设为 `false` 恢复旧的“异常一律放行”。

## 9. 已知边界

| 边界 | 说明 |
|---|---|
| GUI 工具 | Rufus / Ventoy 等在进程内格式化，门禁只看到启动命令，无法判断目标盘 |
| 脚本文件 | `diskpart /s` 与 `regedit /s` 已硬停；但 `powershell -File x.ps1`、`reg import`、`powershell -EncodedCommand` 的内容同样不可见，仍可能漏过 |
| 判定异常 | 只有 critical 层会 fail-closed；普通 R1/R2/R3 遇到内部异常仍按原设计放行 |
| 提权后绕过 | 用户手动在 DSH 外执行不受限制——这是设计意图 |
| 复制语义 | `copy`/`xcopy`/`robocopy`/`Copy-Item` 只看目标；`move` 查源与目标（移走系统文件等于删除） |
| 路径变量 | 展开 `$env:`、`%VAR%`、`~`；解析不了的变量按字面比较，可能漏判（不误报） |
| 误报控制 | 只覆盖破坏性动词，读操作白名单先行；`chkdsk`/`sfc`/`dism` 不进 critical |
| 注册表与沙箱 | 在 `workspace-write` + Low 完整性级别下，写 `HKCU` 也会被 DSH 沙箱拒绝（实测 `reg add` → `file access denied`）。护栏与沙箱是两道独立闸；沙箱放行的写入（如提权后）只剩护栏 |
| 卡片目标 vs 实际地址 | 卡片目标由命令文本推导，不是执行结果。`reg import`/`load`/`restore` 显示的是文件（键在文件内容里不可见）；provider 通配符（`HKCU:\X*`）按字面显示，实际可能匹配多个键。详见 §12 |

## 12. 卡片目标与实际写入/删除地址的一致性

卡片不显示执行结果，只显示从命令文本推出的事实；因此“提示地址 = 实际地址”不是靠一次成功写入证明的，而是逐类论证：

| 形式 | 卡片目标来源 | 与实际地址是否一致 | 风险 |
|---|---|---|---|
| `reg add\|delete HKCU\…` | 第一个 `hk…` token | 一致：`reg.exe` 的键就是第一个位置参数 | 低 |
| 带引号的键、`reg.exe` | 同上，引号被剥掉 | 一致 | 低 |
| `Set-ItemProperty`/`New-Item`/`Remove-Item` + `HK…:` | 第一个 `hk…:` token | 一致：PowerShell 的 `-Path` 就是该 token | 低 |
| `reg import`/`load`/`restore` | 文件路径 | **不一致**：写入的键在文件内容里，卡片只显示文件名 | 中；文件内容不可见，属于设计边界 |
| `HKCU:\X*`、`?` 通配符 | 字面量 | **不一致**：实际可能命中多个键 | 中；卡片未标注“通配符/范围未知” |
| 变量拼接的键（`$env:…`、`%…%`） | 解析不了就空 | 卡片省略目标 | 低；不误报，但信息少 |

结论：常见单目标写法（`reg add`/`reg delete`/provider 精确路径）卡片目标可信；`import/load/restore` 与通配符这两类存在**“提示地址 ≠ 实际地址”**的可能，目前只在文档里标注。

可选的收敛动作（尚未实现）：

1. `registryAction` 为 `import`/`load`/`restore` 时，卡片追加“脚本内容不可见”，避免把文件误读成键；
2. 目标含 `*`/`?` 时追加“含通配符，影响范围未知”；
3. 审计 v2（P2）记录 `displayReason` 与 `outcome`，事后可对照“提示了什么、用户选了什么、最后执行了什么”。
